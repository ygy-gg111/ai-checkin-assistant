# 开发规范（Development Guidelines）

## 一、开发原则

项目开发遵循以下原则：

- 先完成 MVP，再优化架构
- 业务逻辑与页面组件分离
- AI 调用统一走 AI Provider
- Prompt 不写死在业务代码中
- 数据库操作统一通过 Prisma
- API 返回格式统一
- 代码保持简单、清晰、可维护

------

# 二、代码组织规范

项目采用模块化目录结构。

```text
app/              页面与 API Routes
components/       页面组件与公共组件
lib/              核心业务逻辑
prisma/           数据库模型
prompts/          Prompt 模板
types/            全局类型
hooks/            React Hooks
store/            Zustand 状态管理
docs/             项目文档
```

页面层只负责展示和交互。

业务逻辑统一放在：

```text
lib/services/
```

AI 调用统一放在：

```text
lib/ai/
```

数据库操作统一放在：

```text
lib/db/
```

------

# 三、命名规范

## 文件命名

使用小写加短横线：

```text
checkin-form.tsx
image-uploader.tsx
post-card.tsx
prompt-builder.ts
openai-provider.ts
```

## 组件命名

使用 PascalCase：

```tsx
CheckinForm
ImageUploader
PostCard
CalendarView
```

## 函数命名

使用 camelCase：

```ts
generatePost()
uploadImages()
getHistoryList()
buildPrompt()
```

## 常量命名

使用大写下划线：

```ts
MAX_IMAGE_COUNT
DEFAULT_MODEL
UPLOAD_DIR
```

------

# 四、TypeScript 规范

所有核心代码必须使用 TypeScript。

避免使用：

```ts
any
```

如果暂时无法确定类型，优先使用：

```ts
unknown
```

所有 API 入参、返回值、AI 返回结构都应定义类型。

示例：

```ts
export interface GeneratePostRequest {
  topic: string
  dayCount?: number
  style: string
  inputText: string
  images: string[]
}

export interface GeneratePostResult {
  title: string
  content: string
  tags: string[]
  coverText?: string
}
```

------

# 五、API 规范

所有 API 返回统一格式。

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

失败：

```json
{
  "code": 500,
  "message": "error message",
  "data": null
}
```

API Route 中不直接写大量业务逻辑。

推荐结构：

```ts
export async function POST(req: Request) {
  const body = await req.json()

  const result = await checkinService.generate(body)

  return success(result)
}
```

------

# 六、Service 规范

复杂业务逻辑放在 Service 中。

例如：

```text
lib/services/checkin.service.ts
lib/services/history.service.ts
lib/services/calendar.service.ts
lib/services/upload.service.ts
```

Service 负责：

- 参数处理
- 调用数据库
- 调用 AI Provider
- 组织返回结果

Service 不负责页面渲染。

------

# 七、AI 调用规范

业务代码禁止直接调用 OpenAI。

错误示例：

```ts
const openai = new OpenAI()
await openai.responses.create(...)
```

正确方式：

```ts
const aiProvider = getAIProvider()
await aiProvider.generatePost(input)
```

所有 AI 模型调用必须经过：

```text
lib/ai/
```

这样未来切换 Gemini、Qwen、本地模型时，不影响业务层。

------

# 八、Prompt 规范

Prompt 不允许散落在业务代码中。

所有 Prompt 应统一放在：

```text
prompts/
```

或：

```text
lib/prompt/
```

Prompt 修改不应影响业务代码。

Prompt 应按照模块拆分：

```text
system.md
persona.md
swimming.md
running.md
study.md
output-schema.md
```

------

# 九、数据库规范

所有数据库操作统一通过 Prisma。

禁止在业务代码中直接拼接 SQL。

Prisma Client 统一从以下文件导出：

```text
lib/db/prisma.ts
```

数据库字段命名使用 camelCase：

```prisma
createdAt
updatedAt
inputText
checkinDate
```

每张核心表都应包含：

```prisma
createdAt DateTime @default(now())
updatedAt DateTime @updatedAt
```

------

# 十、错误处理规范

统一使用错误处理工具。

建议封装：

```text
lib/utils/response.ts
lib/utils/errors.ts
```

常见错误包括：

- 参数错误
- 未登录
- 文件过大
- AI 调用失败
- 数据不存在
- 数据库异常

错误信息应清晰，但不要暴露敏感信息。

------

# 十一、环境变量规范

所有敏感配置放在 `.env.local`。

示例：

```env
DATABASE_URL="mysql://user:password@localhost:3306/ai_checkin"

OPENAI_API_KEY="sk-xxx"
OPENAI_MODEL="gpt-4o-mini"

JWT_SECRET="your-secret"

UPLOAD_DIR="./uploads"
```

禁止将 `.env.local` 提交到 Git。

------

# 十二、Git 提交规范

提交信息建议使用以下格式：

```text
feat: 新增打卡生成功能
fix: 修复图片上传失败问题
docs: 更新设计文档
style: 调整页面样式
refactor: 重构 AI Provider
chore: 更新依赖
```

常用类型：

```text
feat      新功能
fix       修复
docs      文档
style     样式
refactor  重构
test      测试
chore     构建或依赖
```

------

# 十三、MVP 开发顺序

推荐按以下顺序开发：

```text
1. 初始化 Next.js 项目
2. 配置 Tailwind CSS
3. 配置 Prisma 和 MySQL
4. 创建数据库模型
5. 完成图片上传
6. 完成 AI Provider
7. 完成 Prompt Builder
8. 完成生成接口
9. 完成创建打卡页面
10. 完成历史记录页面
11. 完成日历页面
12. 完成登录功能
13. 优化 UI 与错误处理
```

------

# 十四、代码质量要求

MVP 阶段不追求完美，但必须保证：

- 核心流程可跑通
- 代码结构清晰
- API 返回稳定
- 数据库字段明确
- AI 输出可校验
- Prompt 可维护
- 不写死模型调用逻辑

------

# 十五、后续扩展原则

未来新增功能时，应优先遵循以下方式：

新增 AI 模型：

```text
新增 lib/ai/xxx-provider.ts
```

新增页面：

```text
新增 app/xxx/page.tsx
```

新增业务：

```text
新增 lib/services/xxx.service.ts
```

新增接口：

```text
新增 app/api/xxx/route.ts
```

新增 Prompt：

```text
新增 prompts/xxx.md
```

保持每个模块职责清晰，避免把所有逻辑写在一个文件中。
