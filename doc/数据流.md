# 数据流设计（Data Flow Design）

## 一、设计目标

本项目采用 **Pipeline（流水线）** 的设计思想。

用户的一次打卡操作，将按照固定的数据流依次完成，每个阶段只负责一种职责，保证系统具有良好的可维护性和扩展能力。

整体数据流如下：

```text
用户输入
    │
    ▼
参数校验
    │
    ▼
图片上传
    │
    ▼
Prompt 构建
    │
    ▼
AI Provider
    │
    ▼
JSON 解析
    │
    ▼
数据存储
    │
    ▼
返回前端
```

整个流程中，每个模块职责单一，彼此之间低耦合。

------

# 二、用户操作流程（User Flow）

用户一次完整的操作流程如下：

```text
进入首页
    │
    ▼
点击「创建打卡」
    │
    ▼
上传图片（1~9张）
    │
    ▼
输入今日描述
    │
    ▼
选择文案风格（可选）
    │
    ▼
点击「生成文案」
    │
    ▼
等待 AI 生成
    │
    ▼
查看生成结果
    │
    ▼
一键复制
    │
    ▼
发布到小红书
```

整个流程控制在 **30 秒以内**。

------

# 三、系统业务流程（Business Flow）

系统收到请求后，将按照以下流程处理：

```text
Browser
    │
    ▼
POST /api/checkin/generate
    │
    ▼
参数校验
    │
    ▼
图片上传
    │
    ▼
生成图片 URL
    │
    ▼
读取 Prompt 模板
    │
    ▼
构建最终 Prompt
    │
    ▼
调用 AI Provider
    │
    ▼
解析 AI 返回结果
    │
    ▼
保存数据库
    │
    ▼
返回前端
```

整个流程由 Next.js API Routes 统一负责调度。

------

# 四、AI 工作流（AI Pipeline）

AI 并不是直接根据用户输入生成文案，而是经过多个步骤逐步完成内容生成。

整体流程如下：

```text
用户输入
        │
        ├──────────────┐
        │              │
        ▼              ▼
    上传图片      今日描述
        │              │
        └──────┬───────┘
               ▼
        Prompt Builder
               │
               ▼
      AI Provider（OpenAI）
               │
               ▼
       返回 JSON 数据
               │
               ▼
      JSON 数据校验
               │
               ▼
       返回最终结果
```

整个流程中：

- Prompt Builder 负责组织 Prompt。
- AI Provider 负责调用模型。
- Validator 负责验证 AI 输出结果是否合法。

------

# 五、Prompt 构建流程（Prompt Builder）

为了保证生成内容质量，Prompt 不直接拼接，而是采用模块化构建。

构建流程如下：

```text
System Prompt
        │
        ▼
账号定位（Persona）
        │
        ▼
场景 Prompt
        │
        ▼
用户输入
        │
        ▼
图片内容
        │
        ▼
最终 Prompt
```

例如：

```text
System Prompt

+
普通程序员生活记录

+
游泳打卡模板

+
今天练蛙泳，腿还是不走水

+
上传图片

↓

最终 Prompt
```

这种方式便于后续增加更多模板，而无需修改业务代码。

------

# 六、AI Provider 数据流

AI Provider 是整个 AI 模块的统一入口。

业务层不会直接调用 OpenAI，而是统一调用 AI Provider。

流程如下：

```text
Business Service
        │
        ▼
AI Provider
        │
        ▼
OpenAI GPT-4o mini
        │
        ▼
返回 JSON
```

未来可平滑扩展：

```text
Business Service
        │
        ▼
AI Provider
        │
        ├── OpenAI
        ├── Gemini
        ├── Claude
        ├── Qwen
        └── Local（预留）
```

业务代码无需修改。

------

# 七、数据库数据流

生成成功后，系统将保存完整的打卡记录。

数据流如下：

```text
生成结果
    │
    ▼
保存图片地址
    │
    ▼
保存用户输入
    │
    ▼
保存 AI 返回 JSON
    │
    ▼
保存标题
    │
    ▼
保存正文
    │
    ▼
保存标签
    │
    ▼
保存创建时间
```

最终形成一条完整的打卡记录。

------

# 八、历史记录数据流

用户查看历史记录时：

```text
用户打开历史记录
        │
        ▼
查询数据库
        │
        ▼
返回打卡列表
        │
        ▼
点击查看详情
        │
        ▼
读取完整记录
        │
        ▼
展示标题、正文、标签、图片
```

用户可再次复制文案或删除记录。

------

# 九、错误处理流程

系统发生异常时统一处理。

```text
用户请求
    │
    ▼
参数校验失败
    │
    ├──────────────► 返回错误信息
    │
    ▼
AI 调用失败
    │
    ├──────────────► 返回重试提示
    │
    ▼
数据库保存失败
    │
    ├──────────────► 返回保存失败
    │
    ▼
图片上传失败
    │
    └──────────────► 返回上传失败
```

所有错误统一返回标准 JSON 格式。

------

# 十、完整数据生命周期（Data Lifecycle）

用户一次打卡的数据生命周期如下：

```text
用户上传图片
        │
        ▼
图片保存到 Storage
        │
        ▼
生成图片 URL
        │
        ▼
用户输入今日描述
        │
        ▼
Prompt Builder 构建 Prompt
        │
        ▼
AI Provider 调用 OpenAI
        │
        ▼
AI 返回 JSON
        │
        ▼
JSON 数据校验
        │
        ▼
保存数据库
        │
        ▼
返回前端页面
        │
        ▼
用户复制内容
        │
        ▼
发布到小红书
```

整个数据流遵循 **输入 → 处理 → 输出 → 存储** 的流水线设计，每个模块职责清晰、低耦合，既满足 MVP 快速开发需求，也为后续增加更多 AI 模型和功能扩展预留了充足空间。

# 日历数据流

```
用户进入日历页
      │
      ▼
请求 /api/calendar?year=2026&month=7
      │
      ▼
查询该月 Post.checkinDate
      │
      ▼
按日期聚合
      │
      ▼
返回每一天是否打卡
      │
      ▼
前端渲染日历状态
```

点击某一天：

```
点击日期
      │
      ▼
请求 /api/calendar/day?date=2026-07-03
      │
      ▼
查询当天所有 Post
      │
      ▼
返回内容列表
      │
      ▼
用户点击某条
      │
      ▼
进入历史详情
```
