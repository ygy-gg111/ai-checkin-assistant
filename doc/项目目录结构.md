  # 二、目录说明
  
  ## app/
  
  项目页面与 API 入口。
  
  采用 Next.js App Router。
  
  包含：
  
  - 页面
  - API Routes
  - Layout
  - 路由
  
  ------
  
  ## components/
  
  公共组件目录。
  
  所有页面共享组件统一放置。
  
  例如：
  
  - 图片上传
  - 按钮
  - 编辑器
  - Dialog
  - Card
  
  避免页面中出现大量重复代码。
  
  ------
  
  ## lib/
  
  整个项目最重要的目录。
  
  负责存放所有业务逻辑。
  
  按照职责划分：
  
  - ai：AI Provider
  - prompt：Prompt 管理
  - services：业务服务
  - db：数据库
  - storage：文件存储
  - validators：参数校验
  - utils：公共工具
  
  页面和 API 都通过 lib 调用业务逻辑，实现界面与业务解耦。
  
  ------
  
  ## prisma/
  
  数据库模型与迁移文件。
  
  统一管理：
  
  - 数据模型
  - Migration
  - Seed 数据
  
  所有数据库操作通过 Prisma 完成。
  
  ------
  
  ## prompts/
  
  所有 Prompt 模板统一存放。
  
  不同场景对应不同模板，例如：
  
  - 游泳打卡
  - 跑步打卡
  - 学习记录
  - 日常分享
  
  后续新增模板无需修改业务代码。

  ------

  ## uploads/

  MVP 阶段图片存储目录。
  
  后续可切换：
  
  - 阿里云 OSS
  - Cloudflare R2
  - Amazon S3

  业务代码保持不变。

  ------
  
  ## docs/
  
  项目设计文档。

  包括：

  - 项目设计
  - API 文档
  - 数据库设计
  - 更新日志
  
  方便团队协作与长期维护。
  
  ------

  # 三、目录设计原则

  整个项目遵循以下原则：

  ### 单一职责

  每个目录只负责一种类型的工作，例如：
  
  - ai 负责 AI
  - db 负责数据库
  - storage 负责文件
  - services 负责业务逻辑
  
  避免模块职责混乱。
  
  ------
  
  ### 高内聚、低耦合
  
  页面、业务、AI、数据库相互独立。
  
  例如：
  
  页面不直接调用 OpenAI。
  
  页面 → Service → AI Provider。
  
  这样未来替换 AI 模型时，无需修改页面代码。
  
  ------
  
  ### 可扩展
  
  后续新增：
  
  - Gemini
  - Claude
  - 本地模型
  - OSS
  - Redis
  - Python AI 服务
  
  均可通过新增模块完成，而无需调整现有目录结构。
  
  ------

  ### MVP 优先
  
  当前目录能够满足第一阶段开发需求，同时为后续功能扩展预留空间。
  
  既不过度设计，也避免后期频繁调整项目结构。
