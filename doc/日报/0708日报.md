## 二、今日重点问题与处理记录

### 1. Prompt 页面原有实现与目标不匹配

**现象**：Prompt 设置页已经有 UI，但核心还是本地静态配置，和昨天计划中的“真实联调”目标不匹配。  
**处理**：保留现有页面结构，重写数据来源与交互逻辑，改为接口驱动。  
**结果**：Prompt 页面从“静态展示”推进为“真实管理页面”。

### 2. persona 存在“能保存但不生效”的断层

**现象**：用户设置页的人设可以保存，但生成内容时未进入 Prompt。  
**处理**：抽出 Prompt 组合逻辑，并接入正式生成链路。  
**结果**：人设、模板、输入材料开始共同影响最终生成结果。

### 3. Prompt 模板选择存在“前端选中但后端未必使用”的风险

**现象**：如果只有前端展示模板选择，后端不按模板 ID 拉取真实模板，就会出现“看起来选中了，实际上没生效”。  
**处理**：明确通过 `promptTemplateId` 驱动正式生成与测试生成。  
**结果**：模板选择不再停留在页面层，真实进入后端 Prompt 组装过程。

### 4. token 与字数边界原先只存在隐性风险

**现象**：如果不限制 persona、模板、输入、图片数量和输出 token，后面很容易出现成本不可控、返回结构变差、生成体验波动。  
**处理**：统一建立边界常量，并同时落到后端和前端。  
**结果**：今天已经具备“后端真正限制 + 前端明确提示”的双重约束。

### 5. 本地 / 移动端访问链路排查中暴露出运行态风险

今天下午为了支持手机访问本地页面，做过一轮局域网访问尝试。这个过程虽然不是业务代码开发主线，但确实带来了一些运行态干扰，需要在日报里单独记下来。

**现象**：

- 切换局域网访问后，本地与手机访问链路出现混用
- in-app browser 与本机浏览器的页面状态不一致
- 本地 `next dev` 运行方式切换后，出现“页面能响应，但当前标签页表现异常”的情况
- `dev-server.err.log` 中出现 Next.js dev resource 的跨源阻止提示

**处理过程**：

- 检查了当前监听端口与 node 进程状态
- 在 `127.0.0.1` 与 `0.0.0.0` 两种启动方式之间做过切换排查
- 重新确认本地访问链路与局域网访问链路的差异
- 最终将本地服务关闭，避免继续污染当前环境

**当前结论**：

- 这类“移动端访问本地项目”的需求，后续不能再直接操作
- 以后应先做方案研讨，再决定是否改启动方式、是否改配置、是否改代码
- 移动端联调更适合作为独立方案处理，而不是临时插入到当前本地开发链路里

这段虽然没有形成新的业务代码产出，但属于今天非常关键的一次工程流程复盘。

虽然今天代码级和构建级验证已通过，但完整登录态下的页面链路、接口链路、浏览器状态链路还没有在稳定环境下做完一轮彻底验收。

- 启用 / 停用模板
- 创建页选择模板后正式生成
- 重新生成文案时的模板与边界限制是否一致

### 2. Prompt 设置页与创建页联动仍建议做一次完整业务验收

虽然主链路代码已经打通，但最稳妥的做法仍然是做一次完整业务路径确认：

- Prompt 设置页修改模板
- 创建页选择该模板
- AI 生成结果体现修改后的规则

这一步做完，Prompt 主链路才能算“真正验收完成”。

### 3. 移动端 / 局域网访问类需求后续必须先做方案研讨

今天下午这段过程已经证明，这类需求虽然看起来像“开个访问地址”，实际上会牵动：

- 本地 `127.0.0.1` 开发链路
- 局域网访问链路
- Next dev 热更新资源
- 浏览器当前标签页状态
- 调试方式与验证口径

后续再遇到类似事情，应该优先做：

- 目标界定
- 方案对比
- 影响面说明
- 回退方式说明

确认后再执行。
