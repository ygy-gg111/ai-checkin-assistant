# 登录注册弹窗设计

## 一、设计目标

登录注册功能采用全局弹窗，不单独创建登录页和注册页。

设计目标：

- 用户进入产品后可以先看到完整的 Dashboard 框架。
- 未登录用户首次进入时得到明确的登录提示。
- 用户可以关闭弹窗，以访客状态浏览页面结构。
- 需要用户数据或写操作时，再次自然地引导登录。
- 登录成功后回到用户原本想进行的操作，不打断使用路径。
- PC 和移动端共用同一套认证流程。

------

## 二、核心交互原则

1. 未登录不跳转到独立登录页，保留当前页面上下文。
2. 首次进入应用时，登录弹窗自动出现一次。
3. 用户主动关闭后，本次页面会话内不重复自动弹出。
4. 关闭弹窗不代表登录，页面进入访客空状态。
5. 访客点击受限功能时，重新打开登录弹窗。
6. 注册和登录在同一个弹窗内切换，不改变当前 URL。
7. 注册成功后切回登录表单，并自动填入注册邮箱。
8. 登录成功后关闭弹窗，刷新用户信息和当前页面数据。

------

## 三、认证状态

前端统一维护以下三种认证状态：

```text
loading         正在请求 /api/auth/me，尚不能判断登录状态
guest           未登录或登录凭证已失效
authenticated   已登录并取得当前用户信息
```

页面初始化时不应直接假定用户未登录，以免出现弹窗闪烁。

```text
应用加载
  │
  ▼
请求 GET /api/auth/me
  ├─ 200 → authenticated → 加载用户数据
  ├─ 401 → guest → 首次自动打开登录弹窗
  └─ 5xx → 显示服务异常，不把服务故障伪装成未登录
```

------

## 四、完整用户流程

### 1. 首次进入

```text
进入任意 Dashboard 页面
        │
        ▼
检查当前登录状态
        │
        ├─ 已登录 → 正常加载页面数据
        │
        └─ 未登录 → 自动打开登录弹窗
                        │
                        ├─ 登录成功 → 关闭弹窗并刷新数据
                        ├─ 点击注册 → 切换注册表单
                        └─ 关闭弹窗 → 显示访客空状态
```

### 2. 注册流程

```text
登录弹窗
  │
  └─ 点击「立即注册」
          │
          ▼
      注册表单
          │
          ├─ 注册失败 → 保留输入并显示字段错误
          │
          └─ 注册成功
                │
                ▼
          显示「注册成功，请登录」
                │
                ▼
          切换回登录表单
          自动填入注册邮箱
```

注册成功后暂不自动登录。这样可以让登录逻辑保持唯一入口，也方便后续增加邮箱验证。

### 3. 登录流程

```text
提交邮箱和密码
      │
      ├─ 账号或密码错误 → 显示统一错误，不关闭弹窗
      ├─ 请求过于频繁 → 提示稍后重试
      └─ 登录成功
            │
            ▼
      服务端写入 HttpOnly Cookie
            │
            ▼
      前端更新当前用户
            │
            ▼
      关闭弹窗并刷新当前页面数据
            │
            ▼
      继续执行登录前被拦截的操作
```

### 4. 主动关闭弹窗

用户关闭弹窗后：

- 不跳转页面。
- 不伪造默认用户或 Mock 数据。
- 历史记录、日历、个人数据展示访客空状态。
- 页面明确显示「登录后查看数据」或「登录后开始打卡」。
- 点击空状态按钮或任何受限操作，再次打开登录弹窗。

## 五、弹窗结构

### 1. 登录模式

```text
┌─────────────────────────────────────┐
│ ✦ AI Check-in                  关闭 │
│                                     │
│ 欢迎回来                            │
│ 登录后继续记录普通而具体的每一天    │
│                                     │
│ 邮箱                                │
│ [ name@example.com                ] │
│                                     │
│ 密码                                │
│ [ ••••••••                    显示 ] │
│                                     │
│ [              登录              ] │
│                                     │
│ 还没有账号？立即注册                │
└─────────────────────────────────────┘
```

登录表单字段：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 邮箱 | 是 | 去除首尾空格并转为小写，校验邮箱格式 |
| 密码 | 是 | 8～128 个字符，不在前端记录明文 |

### 2. 注册模式

```text
┌─────────────────────────────────────┐
│ ✦ AI Check-in                  关闭 │
│                                     │
│ 创建账号                            │
│ 从今天开始保存自己的成长记录        │
│                                     │
│ 昵称（选填）                        │
│ [ 普通记录者                      ] │
│                                     │
│ 邮箱                                │
│ [ name@example.com                ] │
│                                     │
│ 密码                                │
│ [ ••••••••                    显示 ] │
│                                     │
│ 确认密码                            │
│ [ ••••••••                        ] │
│                                     │
│ [            创建账号            ] │
│                                     │
│ 已有账号？返回登录                  │
└─────────────────────────────────────┘
```

注册表单字段：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| 昵称 | 否 | 最多 100 个字符；为空时使用邮箱前缀 |
| 邮箱 | 是 | 有效邮箱，最多 191 个字符 |
| 密码 | 是 | 8～128 个字符 |
| 确认密码 | 是 | 必须与密码一致，仅前端使用，不传给 API |

## 六、弹窗触发规则

### 自动触发

- 应用初始化完成且 `/api/auth/me` 返回 401。
- 每次完整页面会话只自动触发一次。
- 语言切换、普通路由切换不应反复自动触发。

### 用户行为触发

未登录时执行以下操作应打开登录弹窗：

- 创建打卡或生成文案。
- 上传需要持久化的图片。
- 查看历史记录详情。
- 查看个人日历数据。
- 修改 Prompt 模板。
- 编辑用户资料。
- 点击用户头像或「登录」按钮。

### API 触发

业务请求返回 401 时：

1. 将全局认证状态更新为 `guest`。
2. 清空过期的前端用户信息。
3. 保存当前待执行操作。
4. 打开登录弹窗。
5. 登录成功后重新请求一次原操作。

不得对 401 进行无限自动重试。

------

## 七、访客空状态

用户关闭登录弹窗后，页面可以浏览，但不展示其他用户或 Mock 数据。

| 页面 | 访客状态 |
| --- | --- |
| Dashboard | 统计数字显示 `--`，最近记录显示登录引导 |
| 创建打卡 | 可以查看表单；上传、生成或保存时要求登录 |
| 打卡日历 | 显示空日历和「登录后查看打卡记录」 |
| 历史记录 | 显示空列表和「登录后查看历史记录」 |
| Prompt 设置 | 可以查看说明；编辑、测试和保存时要求登录 |
| 用户设置 | 显示未登录状态和登录按钮 |

空状态统一包含：

- 简洁图标。
- 当前页面对应的说明文字。
- 一个明确的「登录」主按钮。
- 可选的「创建账号」次级入口。

------

## 八、接口约定

### 1. 获取当前用户

```text
GET /api/auth/me
```

已登录返回 `200`：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "user": {
      "id": "user_id",
      "email": "name@example.com",
      "name": "普通记录者",
      "avatar": null,
      "createdAt": "2026-07-06T10:00:00.000Z"
    }
  }
}
```

未登录或 Cookie 失效返回 `401`。

### 2. 注册

```text
POST /api/auth/register
```

请求：

```json
{
  "name": "普通记录者",
  "email": "name@example.com",
  "password": "用户密码"
}
```

成功返回 `201`。当前接口已经接入 Prisma，并使用带随机盐的 `scrypt` 保存密码哈希。

错误约定：

| HTTP 状态 | 场景 |
| --- | --- |
| 400 | 参数格式不正确 |
| 409 | 邮箱已注册 |
| 500 | 服务或数据库异常 |

### 3. 登录

```text
POST /api/auth/login
```

请求：

```json
{
  "email": "name@example.com",
  "password": "用户密码"
}
```

成功后由服务端写入 `auth_token` HttpOnly Cookie，并返回不包含密码字段的用户信息。

错误约定：

| HTTP 状态 | 场景 |
| --- | --- |
| 400 | 参数格式不正确 |
| 401 | 邮箱或密码错误 |
| 429 | 请求过于频繁 |
| 500 | 服务异常 |

为避免泄露账号是否存在，邮箱不存在和密码错误统一提示「邮箱或密码错误」。

### 4. 退出登录

```text
POST /api/auth/logout
```

服务端清除认证 Cookie，前端切换为访客状态并显示空数据。

## 九、前端组件规划

建议新增：

```text
src/
├── components/
│   └── auth/
│       ├── auth-modal.tsx
│       ├── login-form.tsx
│       ├── register-form.tsx
│       └── guest-empty-state.tsx
├── contexts/
│   └── auth-context.tsx
├── hooks/
│   └── use-auth.ts
└── lib/
    └── auth/
        ├── password.ts
        └── session.ts
```

核心职责：

### `AuthProvider`

- 请求当前用户。
- 保存 `loading / guest / authenticated` 状态。
- 提供 `openAuthModal()`、`closeAuthModal()`、`login()`、`logout()`。
- 保存登录前待执行的操作。

### `AuthModal`

- 控制登录与注册模式切换。
- 控制关闭行为和表单状态。
- 注册成功后切回登录模式并保留邮箱。

### `GuestEmptyState`

- 为 Dashboard、历史、日历等页面提供统一访客提示。
- 点击主按钮打开登录弹窗。

## 十、Cookie 与安全要求

认证 Cookie 建议设置：

```ts
{
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  path: '/',
  maxAge: 60 * 60 * 24 * 7
}
```

安全要求：

- Token 不存入 `localStorage` 或可被前端脚本读取的 Cookie。
- API 不返回 `passwordHash`。
- 前后端都执行参数校验，后端校验为最终依据。
- 登录错误不区分邮箱不存在和密码错误。
- 登录接口后续增加 IP/账号维度的限流。
- 修改资料、删除记录等写操作需要考虑 CSRF 防护。
- 服务端日志不得记录密码、Cookie 或完整 Token。

## 十一、响应式与国际化

### PC

- 弹窗宽度建议为 440～480px。
- 表单保持单列布局。
- 页面背景保留 Dashboard，使用半透明遮罩。

### 移动端

- 宽度小于 576px 时使用接近全屏的 Modal 或 Drawer。
- 输入框高度至少 44px。
- 避免键盘弹起后遮挡提交按钮。

### 国际化

- 所有标题、字段名、按钮、错误提示写入 `messages/zh-CN.json` 和 `messages/en.json`。
- 后端错误以稳定错误码为主，前端根据错误码显示当前语言文案。

## 十二、实现顺序

1. 完成真实登录接口和会话签发逻辑。
2. 完成 `/api/auth/me` 的真实 Cookie 校验。
3. 完成退出登录接口。
4. 新增 `AuthProvider` 和 `useAuth`。
5. 新增登录/注册弹窗及表单切换。
6. 新增统一访客空状态。
7. 接入受限操作和 API 401 处理。
8. 补齐中英文文案。
9. 完成 PC、移动端和会话过期测试。

------

## 十三、验收标准

- 未登录首次进入时，登录弹窗只自动出现一次。
- 用户可以关闭弹窗并停留在原页面。
- 关闭后所有用户数据区域显示明确的访客空状态。
- 点击受限功能可以再次打开登录弹窗。
- 登录和注册可以在弹窗内来回切换。
- 注册成功后自动切回登录，并保留注册邮箱。
- 重复邮箱注册显示明确提示。
- 错误密码不会关闭弹窗，也不会泄露账号是否存在。
- 登录成功后弹窗关闭，用户信息和当前页面数据立即刷新。
- 登录成功后可以继续执行登录前被拦截的操作。
- Cookie 过期后，下一次受限请求返回 401 并重新弹出登录框。
- 刷新页面后，有效登录状态能够恢复。
- 退出登录后回到访客空状态。
- 响应和日志中均不出现密码或密码哈希。

------

## 十四、暂不实现

第一阶段暂不包含：

- 忘记密码和重置密码。
- 邮箱验证码与邮箱验证。
- 微信、GitHub 等第三方登录。
- 多设备会话管理。
- 管理员和普通用户角色体系。
- 强制用户登录后才能看到任何页面。

这些能力可以在核心注册、登录和打卡流程稳定后再逐步加入。
